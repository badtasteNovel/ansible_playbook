# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This repository hosts Ansible automation to provision a Debian 13 (trixie) VM on an ESXi host (not local containers/WSL — local host memory is insufficient for that) via a fully unattended (preseed) install, and configure it, including generating and distributing an SSH key. Networking is DHCP. First target VM: `debian-vm`, sudo user `charlie`, no password on that account at all (locked, SSH-key-only, passwordless sudo) — there's no console/rescue path by design, since SSH access exists from first boot.

The `community.vmware` module parameter names and return-field shapes used in `build_vm/debian.yml` (especially `vmware_guest_boot_manager`, `vsphere_copy`'s datastore path format, and `vmware_guest_info`'s IP field) were written from general knowledge, not verified against a live collection or ESXi host — there's neither `ansible-playbook` nor ESXi access in the dev sandbox. Run `ansible-doc community.vmware.<module>` against the installed collection version before trusting this end-to-end, and expect to need adjustments.

`custom/scripts/remaster-iso/debian.sh` has been run end-to-end against the real Debian 13.7.0 netinst ISO and a real rendered `preseed.cfg` (extraction, all the `sed`/config edits, and the final `xorriso -as mkisofs` repack) — the script no longer uses `mount`/`sudo` at all (see below), so this needed no special sandbox access. The repacked ISO's El Torito boot record (both BIOS and UEFI images present) and the presence/content of the injected `preseed.cfg`, `isolinux.cfg`, `gtk.cfg` were all re-extracted and checked. What's still unverified: actually booting that ISO in a real VM — no ESXi access in the dev sandbox.

**Gotcha confirmed by direct test**: `ansible.builtin.command`'s working directory is the directory *containing the playbook file* (e.g. `build_vm/`), not the directory `ansible-playbook` was invoked from. Any relative path handed to a `command:` task (like `iso_path`, passed in via `--extra-vars`) must be absolute, or it'll silently resolve against the wrong base and fail in confusing ways (this is what caused a `mount`/loop-device-looking failure that was actually just "file not found" the whole time). `select-iso` and `build:debian` both build `iso_path` with `$(pwd)/...` for exactly this reason — Task itself reliably runs with cwd = the root `Taskfile.yaml`'s directory (confirmed separately), so `$(pwd)` there is safe.

## Directory layout: official Ansible skeleton vs. `custom/`

Ansible's own documented project layout (inventory, `group_vars/`, `host_vars/`, `roles/`, top-level playbooks) only covers things Ansible itself understands — it says nothing about where project-specific tooling belongs, since that's out of Ansible's scope by design. This repo keeps that distinction explicit:

- **Repo root** — the official skeleton, plus files tools require to live at root: `inventory/`, `group_vars/`, `host_vars/` (currently empty, held by `.gitkeep`), `roles/`, `build_vm/` (top-level playbooks, one file per OS/distro — currently just `build_vm/debian.yml`; the sample-setup doc doesn't dictate playbook names any more than it dictates this grouping, so this is our own convention sitting alongside the official pieces, not inside `custom/`), `Taskfile.yaml` (by the user's preference, not an Ansible convention), `.gitignore` and `CLAUDE.md` (must stay at root for git/Claude Code to find them), and `requirements.yml` (not from Ansible's sample-setup doc specifically, but a near-universal `ansible-galaxy` convention — kept at root; revisit if that's wrong).
- **`custom/`** — everything else: ISO handling (`custom/iso/`), build output (`custom/generated/`), the generated SSH keypair (`custom/keys/`), helper scripts (`custom/scripts/`), and the `.env`/`.env.example` pair. None of this is Ansible-recognized; it's purely this project's own convention.

## Commands

- `task --list` — list available tasks
- `task install` — install local tooling; runs `install:default` from the included `install` namespace, which calls `install:ansible` (ansible-core + collections from `requirements.yml` + `python3-pyvmomi`, the Python library `community.vmware` needs to talk to the vSphere API — collections don't auto-install their own Python deps), `install:iso-tools` (`xorriso`, `isolinux`), `install:gum`, and `install:jq`
- `task select-iso` — interactively pick an OS registered in `custom/iso/manifest.json` (via `gum choose`), prints the resolved ISO path; fails if the file isn't actually present under `custom/iso/`
- `task build:debian` — sources `custom/.env`, looks up `manifest.json`'s `debian` entry (`iso-path` + `build-path`) directly (no interactive prompt — the task name already says which OS), then runs `ansible-playbook <build-path>` with the resolved ISO path

## Architecture

- `Taskfile.yaml` — root task definitions; includes namespaced task files from `custom/scripts/tasks/` (e.g. `custom/scripts/tasks/install.yaml` as the `install` namespace, `build-vm.yaml` as `build`, `verify-iso.yaml` as `verify-iso`). Add new task groups the same way rather than growing the root file.
- `custom/iso/manifest.json` — maps an OS name to `{"iso-path": "<path under custom/iso/>", "build-path": "<playbook path>"}`. This is the single source of truth both `select-iso`/`verify-iso` (which only need `iso-path`) and `build:*` (which needs both — it looks up `build-path` to know which playbook to run, instead of any task hardcoding a playbook filename) read from.
- `custom/iso/` — holds *source* ISO files used to provision VMs. Has its own scoped `.gitignore` (ignore everything except `manifest.json` and itself) rather than relying on the root `.gitignore`; place the actual ISO files here manually before running tasks that need them (e.g. `custom/iso/debian/<filename>`, matching the `iso-path` registered in `manifest.json`).
- `custom/scripts/verify-iso/debian.sh` — verifies a Debian ISO is an unmodified official release, entirely at run time with no long-lived trust material committed to the repo: interactively confirms (via `read`, defaulting to the `current` mirror directory) where to fetch `SHA512SUMS`/`SHA512SUMS.sign` from, downloads the three Debian CD signing keys fresh from `debian.org/CD/key-<id>.txt` and checks their fingerprints against constants pinned in the script, *also* cross-checks those pinned constants against what `debian.org/CD/verify` currently publishes (hard-fails on any mismatch — this exists to catch the script's own pinned values going stale, not just a compromised download), then `gpgv`-verifies the signature and `sha512sum -c`s the ISO itself. Usage: `debian.sh <path/to/iso>`. Verified end-to-end against the real Debian 13.7.0 netinst ISO and its real official `SHA512SUMS`/`SHA512SUMS.sign` — this one isn't a "hasn't been tested yet" caveat like some of the other scripts in this repo.
- `custom/generated/` — build output produced by the playbook at runtime, split by role: `custom/generated/preseed/preseed.cfg` is the rendered template (an intermediate input that gets embedded into the ISO, not a deliverable itself), `custom/generated/iso/<vm_name>-preseed.iso` is the actual deliverable that gets uploaded to ESXi. Kept separate from `custom/iso/` (source material) on purpose.
- `build_vm/debian.yml` — the main entry point, at repo root alongside `roles/`/`inventory/`. Runs entirely against `localhost` (it shells out and calls the ESXi API; it doesn't SSH anywhere until the very last step). Flow: generate an SSH keypair under `custom/keys/` (gitignored) → render `roles/debian_preseed_iso/templates/preseed.cfg.j2` into `custom/generated/preseed/` → remaster the selected ISO via `custom/scripts/remaster-iso/debian.sh` into `custom/generated/iso/` → upload it to the ESXi datastore (`community.vmware.vsphere_copy`) → create the VM (`community.vmware.vmware_guest`, `state: present`) → set CD-first boot order (`vmware_guest_boot_manager`) → power on → poll `vmware_guest_info` until an IP shows up → wait for port 22.
- `custom/scripts/remaster-iso/` — per-OS ISO remastering scripts, one file per distro/installer family (currently just `debian.sh`, for the classic Debian Installer/isolinux-grub layout). `debian.sh` extracts a Debian netinst ISO (read-only, via `xorriso -osirrox` — no `mount`/`sudo`/loop device needed, which also sidesteps environments where `mount -o loop` fails), drops in `preseed.cfg`, then: sets `isolinux.cfg`'s `timeout` to a short value (its default, `timeout 0`, means *wait forever for a keypress* in syslinux, not "boot immediately" — a real gotcha), adds the preseed kernel args to both `isolinux/gtk.cfg` (the entry actually marked `menu default`) and `isolinux/txt.cfg` (the text-mode fallback), and for the UEFI path inserts `set timeout=1` / `set default=0` plus the preseed args into only the *first* `menuentry` in `boot/grub/grub.cfg` (that file has ~19 matching kernel lines across rescue/speech/dark-theme variants — don't blindly patch all of them). Repacks with `xorriso`, using `/usr/lib/ISOLINUX/isohdpfx.bin` from the system's `isolinux` package (installed by `install:iso-tools`) for the isohybrid MBR — that file does *not* exist inside the source ISO itself, despite what an earlier version of this script assumed.
- VM provisioning target: a standalone ESXi host (no vCenter) — `community.vmware` modules are called with `datacenter: ha-datacenter`, the implicit pseudo-datacenter name for a bare ESXi host.
- Secrets (ESXi hostname/credentials/datastore/network) live in `custom/.env`, gitignored; `custom/.env.example` documents the required keys and is the tracked template. The playbook reads these via `lookup('env', ...)`, so anything invoking `ansible-playbook` must source `custom/.env` first (the `build:debian` task does this). Treat `custom/.env` as off-limits to read directly once the user has filled it in with real values — ask them to confirm things themselves instead.
- SSH key handling: the keypair is generated locally by the playbook (`community.crypto.openssh_keypair`, under `custom/keys/`); only the public key is baked into the preseed `late_command` and ends up on the VM. The private key never leaves the control node and is never committed.
