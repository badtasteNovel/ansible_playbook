# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This repository hosts Ansible automation to build a Debian 13 (trixie) VM for a standalone ESXi host (no vCenter) via a fully unattended (preseed) install, including generating and distributing SSH keys. Networking is DHCP. First target VM: `debian-vm`, sudo user `charlie`, no password on that account at all (locked, SSH-key-only, passwordless `NOPASSWD` sudo).

**Deliberately does not use any vSphere/ESXi API** — no `pyvmomi`, no `community.vmware`. An earlier version drove ESXi through that collection and hit a chain of real bugs (version-mismatched `pyvmomi`/`community.vmware` pairs, a module-internal `VmomiJSONEncoder` incompatibility, a `cdrom` param validation bug, `esxi_hostname`-vs-connection-`hostname` name confusion, a 10-second default upload timeout for a ~1GB file) — all symptoms of depending on that collection at all, not of this project's own code. The replacement: build everything locally (ISO, `.vmx`, SSH keys), `scp` the ISO and `.vmx` to the datastore over plain SSH, create the disk with `vmkfstools` (a local ESXi CLI tool, not an API call) over the same SSH connection, and stop there. **Registering the VM (Host Client → browse datastore → "Register VM") and powering it on are manual, by design** — that's the one step that inherently touches ESXi's inventory/management layer, and keeping it manual means the automation here never does.

`.vmx` file syntax and `vmkfstools` usage were written from general VMware documentation knowledge, not verified against a live ESXi host — there's no ESXi access in the dev sandbox. The `.vmx`'s `guestOS = "debian12-64"` is a guess (Debian 13 doesn't have its own guestOS string yet in older ESXi catalogs); `virtualHW.version = "15"` was picked as a conservative floor (supported since ESXi 6.7) to maximize compatibility — bump it if the real host supports newer.

**SSH host key is pre-generated, not left to chance**: the playbook generates a *second* keypair (`custom/generated/keys/<vm_name>_host_ed25519`, separate from `charlie`'s client keypair) and copies both halves into the ISO's injection payload; the preseed `late_command` copies them over `/etc/ssh/ssh_host_ed25519_key(.pub)`, overwriting whatever `openssh-server`'s postinst already auto-generated. This means the host key's fingerprint is known *before* the VM ever boots — no need to `ssh-keyscan` a live host and no race condition waiting for SSH to come up. Files are copied as-is (`cp /cdrom/ssh_host_key ...`), not embedded as text in `late_command` — preseed's `late_command string` is effectively one `sh -c` line, and a multi-line private key has no safe way to survive that as an inline string (no heredocs, uncertain whether `base64` is even present in the installer's minimal shell); shipping the key as a real file inside the ISO sidesteps the whole problem.

Other gotchas confirmed by direct testing in this repo's history (see git log for the specifics): `ansible.builtin.command`'s working directory is the directory *containing the playbook file*, not the directory `ansible-playbook` was invoked from — any relative path handed to a `command:` task must be absolute (`select-iso` and `build:debian` build `iso_path` with `$(pwd)/...` for exactly this reason, since Task itself reliably runs with cwd = the root `Taskfile.yaml`'s directory).

## Directory layout: official Ansible skeleton vs. `custom/`

Ansible's own documented project layout (inventory, `group_vars/`, `host_vars/`, `roles/`, top-level playbooks) only covers things Ansible itself understands — it says nothing about where project-specific tooling belongs, since that's out of Ansible's scope by design. This repo keeps that distinction explicit:

- **Repo root** — the official skeleton, plus files tools require to live at root: `inventory/`, `group_vars/`, `host_vars/`, `roles/` (all three of `group_vars/`, `host_vars/`, `roles/` are currently empty, each held by a `.gitkeep` — this project never ended up using real Ansible roles, see below, so `roles/` is reserved/unused on purpose rather than repurposed), `playbook/` (top-level playbooks, grouped by which side of the WireGuard tunnel they configure — `playbook/control-panel/debian.yml` builds the VM, `playbook/wsl/add-peer.yml` adds the control node as a WireGuard peer), `Taskfile.yaml` (by the user's preference, not an Ansible convention), `.gitignore` and `CLAUDE.md` (must stay at root for git/Claude Code to find them), and `requirements.yml` (a near-universal `ansible-galaxy` convention, kept at root).
- **`custom/`** — everything else: ISO handling (`custom/iso/`), build output (`custom/generated/`), the generated SSH keypairs (`custom/generated/keys/`), helper scripts (`custom/scripts/`), the `.env`/`.env.example` pair, and two subdirectories that used to live under `roles/*/` before a cleanup pass moved them out (see below for why): `custom/scripts/tasks/ansible/` (reusable Ansible task fragments, included via `include_tasks` with an explicit path — e.g. `custom/scripts/tasks/ansible/wireguard_keys/`, `custom/scripts/tasks/ansible/load_env/`) and `custom/config/` (Jinja2 templates rendered via `ansible.builtin.template` — e.g. `custom/config/debian_preseed_iso/`, `custom/config/wireguard_control_panel/`, `custom/config/wireguard_agent/`). None of this is Ansible-recognized; it's purely this project's own convention. `custom/scripts/tasks/` itself splits into `go-task/` (the Taskfile namespace files — `install.yaml`, `build-vm.yaml`, `verify-iso.yaml`, `windows.yaml`) and `ansible/` (the task fragments above) — same top-level folder, two different tools' files, kept apart so the name alone doesn't make you guess which kind a given file is.

**Why the `roles/*/` content moved out**: it was never actually using Ansible's role mechanism to begin with — real roles can't declare their own `hosts:` (that's a play's job), and this project's `include_tasks`/`template` calls always spelled out the full explicit path (`{{ playbook_dir }}/../../roles/...`) rather than relying on `include_role`'s automatic role-relative path resolution, because `include_role`'s search path only checks `roles/` relative to the *playbook's own directory*, which this project's `playbook/control-panel/roles/` never had (confirmed by direct testing — see the WireGuard section below). So the `roles/` directory name was borrowed purely for familiarity, while every file in it was in practice just a plain task-fragment/template file reached by hardcoded path — indistinguishable, mechanically, from anything living under `custom/`. Once that was pointed out, the content moved to where it actually semantically belongs (`custom/`), and `roles/` went back to being an unused, reserved part of the official skeleton, matching `group_vars/`/`host_vars/`.

## Commands

- `task --list` — list available tasks
- `task install` — install local tooling; runs `install:default` from the included `install` namespace: `install:ansible` (ansible-core + collections from `requirements.yml`), `install:iso-tools` (`xorriso`, `isolinux`), `install:gum`, `install:jq`, `install:sshpass` (needed so `build:debian` can SSH into the hypervisor non-interactively via `SSHPASS`), `install:wireguard-tools` (`wg`/`wg-quick`, needed locally to generate WireGuard keys — WireGuard is a mandatory part of every build, not optional, so this is needed on every machine that runs `build:debian`)
- `task select-iso` — interactively pick an OS registered in `custom/iso/manifest.json` (via `gum choose`), prints the resolved ISO path; fails if the file isn't actually present under `custom/iso/`
- `task verify-iso` — interactively pick an OS, verify its registered ISO is an unmodified official release
- `task build:debian` — `gum confirm`s whether to add *this* machine as a WireGuard peer of the VM being built (runs `playbook/wsl/add-peer.yml` first if so — see the WireGuard section below; declining this just means no machine is enrolled as a peer yet, not that the VM skips WireGuard — it never does), `gum confirm`s before repackaging an already-existing local ISO and before overwriting an already-existing remote datastore folder, sources `custom/.env`, looks up `manifest.json`'s `debian` entry (`iso-path` + `build-path`), runs `ansible-playbook <build-path>` with the resolved ISO path. Produces and uploads everything; does **not** register or power on the VM — the task's final `debug` output tells you what to do manually, including the exact `known_hosts` line to add once you know the VM's IP.

## Architecture

- `Taskfile.yaml` — root task definitions; includes namespaced task files from `custom/scripts/tasks/go-task/` (`install.yaml` as `install`, `build-vm.yaml` as `build`, `verify-iso.yaml` as `verify-iso`, `windows.yaml` as `windows`). Add new task groups the same way rather than growing the root file.
- `custom/iso/manifest.json` — maps an OS name to `{"iso-path": "<path under custom/iso/>", "build-path": "<playbook path>"}`. Single source of truth for both `select-iso`/`verify-iso` (only need `iso-path`) and `build:*` (needs both, to know which playbook to run without any task hardcoding a filename).
- `custom/iso/` — holds *source* ISO files. Scoped `.gitignore` (ignore everything except `manifest.json` and itself); place actual ISO files here manually, e.g. `custom/iso/debian/<filename>` matching the registered `iso-path`.
- `custom/scripts/verify-iso/debian.sh` — verifies a Debian ISO is an unmodified official release, entirely at run time with no long-lived trust material committed to the repo: `read`-prompts for the mirror directory (default `current`, which also doubles as a "new release available" signal if the ISO's filename no longer matches what that directory serves), downloads the three Debian CD signing keys fresh from `debian.org/CD/key-<id>.txt`, checks their fingerprints against constants pinned in the script, cross-checks those pinned constants against what `debian.org/CD/verify` currently publishes (hard-fails on any mismatch), then `gpgv`-verifies the signature and `sha512sum -c`s the ISO. Usage: `debian.sh <path/to/iso>`. Verified end-to-end against the real Debian 13.7.0 netinst ISO — not a "hasn't been tested" caveat like some other scripts here.
- `custom/generated/` — build output, split by role and namespaced per VM name (so building multiple VMs doesn't have them overwrite each other's files): `custom/generated/preseed/<vm_name>/` holds `preseed.cfg` plus copies of the pre-generated host-key files (the full *injection payload* that gets copied into the ISO — an intermediate input, not a deliverable itself); `custom/generated/iso/<vm_name>/` holds the actual deliverables, the repacked ISO and the rendered `.vmx`.
- `playbook/control-panel/debian.yml` — the main entry point for building the VM (named "control-panel" because this VM is also the WireGuard server — see the WireGuard section below). Runs entirely against `localhost`. Flow: generate the `charlie` client keypair and a separate VM host keypair under `custom/generated/keys/` → copy both host-key files into `custom/generated/preseed/<vm_name>/` → render `preseed.cfg` there → remaster the ISO via `custom/scripts/remaster-iso/debian.sh` into `custom/generated/iso/<vm_name>/` → render `debian.vmx` into the same dir → SSH into the hypervisor to `mkdir` `/vmfs/volumes/<datastore>/<vm_name>/`, `scp` the ISO and `.vmx` there, and run `vmkfstools` there to create the disk (`<vm_name>.vmdk`) — the `.vmx`'s disk/cdrom references are bare filenames, not full paths, relying on all three files sitting in that same remote folder together. Ends there; see "Project status" above for why registration/power-on aren't automated.
- `custom/scripts/remaster-iso/debian.sh` — now takes `<source.iso> <extra_files_dir> <output.iso>` (previously just a single `preseed.cfg` path) — everything in `extra_files_dir` gets copied to the repacked ISO's root, since there are now multiple files to inject (`preseed.cfg`, `ssh_host_key`, `ssh_host_key.pub`). Extracts read-only via `xorriso -osirrox` (no `mount`/`sudo`/loop device). Boot automation needs two layers: (1) add the preseed kernel args to the menu entry that's actually auto-selected — BIOS: `isolinux/gtk.cfg`'s `installgui` (has the real `menu default` flag; `isolinux/txt.cfg`'s `install` is just the text-mode fallback, patch both to be safe) and UEFI: only the *first* `menuentry` in `boot/grub/grub.cfg` (that file has ~19 matching kernel lines across rescue/speech/dark-theme variants — don't patch all of them); (2) force a short menu timeout, since the defaults mean *wait forever for a keypress* (isolinux's `timeout 0` is a special "disabled" value, not "0 seconds"; grub has no timeout/default set at all). Repacks with `xorriso`, using `/usr/lib/ISOLINUX/isohdpfx.bin` from the system's `isolinux` package for the isohybrid MBR — that file does not exist inside the source ISO itself.
- `custom/config/debian_preseed_iso/preseed.cfg.j2` / `debian.vmx.j2` — the two Jinja2 templates rendered by `playbook/control-panel/debian.yml`.
- Secrets (hypervisor hostname/credentials/datastore/network) live in `custom/.env`, gitignored; `custom/.env.example` documents the required `HYPERVISOR_*` keys (named generically, not `ESXI_*`, since nothing here is actually ESXi-API-specific anymore — swapping to a different SSH-reachable hypervisor would mainly mean writing a different `.vmx`-equivalent template) and is the tracked template. The playbook reads these via `lookup('env', ...)`; `build:debian` sources `.env` before invoking `ansible-playbook`. Treat `custom/.env` as off-limits to read directly once the user has filled it in with real values — ask them to confirm things themselves instead.
- SSH to the hypervisor uses `sshpass -e` (password via the `SSHPASS` env var, set per-task via Ansible's `environment:`, never passed as a literal `-p` argument) — deliberately chosen over setting up SSH keys for the hypervisor connection, after discussing the risk (password briefly visible to other local processes/users via `ps`/`/proc` during the connection — low-severity on a single-user control node, which this project already assumes given `.env` holds plaintext secrets regardless).
- SSH key handling: both the `charlie` client keypair and the VM's host keypair are generated locally (`community.crypto.openssh_keypair`, under `custom/generated/keys/`). Only public halves + the full host keypair get baked into the ISO; client *private* keys never leave the control node and are never committed.

## WireGuard (mandatory, not optional)

Every `debian-vm` build is a WireGuard server — there is no toggle for this, no `enable_wireguard`-style variable anywhere, and no way to build the VM without it. This was a deliberate correction: an earlier version of this feature gated the whole thing behind an `enable_wireguard` extra-var, and the user explicitly rejected that framing — WireGuard is a hard requirement of every build, full stop. The VM (`playbook/control-panel/debian.yml`) is named "control-panel" specifically because it's also the WireGuard **server**; the control node running `ansible-playbook` (in practice, the user's WSL2 machine) can be enrolled as a **peer** via `playbook/wsl/add-peer.yml`.

The *only* thing that's actually optional is whether the current machine gets enrolled as a peer in any given `build:debian` run — `custom/scripts/tasks/go-task/build-vm.yaml`'s `gum confirm` asks exactly that, nothing more. Declining it does not disable WireGuard on the VM; it just means no peer gets added this run (the VM still comes up as a WireGuard server with a pre-generated, as-yet-unclaimed peer slot — see below). The file is named `add-peer.yml`, not `agent.yml`, on purpose: being added as a WireGuard peer doesn't imply this machine becomes a cluster "agent" node of anything (there's no cluster — no k3s or similar has been set up in this project at all) — it was named that way once and renamed after the user pointed out the misleading implication.

- `custom/scripts/tasks/ansible/wireguard_keys/` — key generation/allocation shared by both playbooks, split into four task fragments (all included via `ansible.builtin.include_tasks` with an explicit `{{ playbook_dir }}/../../custom/scripts/tasks/ansible/wireguard_keys/<file>.yml` path, not `ansible.builtin.include_role` — see the `custom/` note above for why):
  - `vm_key.yml` — generates just the VM's own WireGuard keypair (`wg genkey`/`wg pubkey` shelled out via `ansible.builtin.shell`, `args.executable: /bin/bash` since the pipeline needs `pipefail` and `/bin/sh` on this system is dash), idempotent via `creates:`. `control-panel/debian.yml` calls this unconditionally on every build; `add-peer.yml` calls the exact same file (it needs the VM's public key to render its own `wg0.conf`), so whichever one runs first actually generates the keypair, and the other just sees `creates:` already satisfied.
  - `generate_one_peer_slot.yml` — batch-creates N anonymous peer slots (keypair + PresharedKey + an IP address derived from an incrementing `peerN` directory name) under `custom/generated/keys/wireguard-keys/wireguard_peers/`, called in a loop by `control-panel/debian.yml` based on `peer_slot_count`. Deliberately produces *unclaimed* material only — which machine eventually uses a given slot is a separate concern, handled by the next two files.
  - `claim_peer.yml` — picks the first not-yet-claimed peer slot (glob + check for a `claimed` marker file) and returns its name as `claimed_peer_name`. Does **not** write the marker itself.
  - `mark_peer_claimed.yml` — writes the `claimed` marker for a given peer name, passed in as `peer_to_claim`. Deliberately split from `claim_peer.yml`: the marker is only written after the caller's own setup (reading the keys, rendering `wg0.conf`, `wg-quick up`) has actually succeeded, so a mid-flow failure doesn't permanently waste a peer slot — `add-peer.yml` calls this right after each of its two tunnels (WSL2, native Windows) is confirmed working, not right after `claim_peer.yml` returns.
- `custom/config/wireguard_control_panel/wg0.conf.j2` — the VM's own `wg0.conf` (server: `Address = 10.105.0.1/24`, `ListenPort`, one `[Peer]` block per currently-existing peer slot, claimed or not). Rendered into `custom/generated/preseed/<vm_name>/wg0.conf` by `control-panel/debian.yml`, injected into the ISO the same way the SSH host key is, copied to `/etc/wireguard/wg0.conf` by preseed's `late_command`, unconditionally, every build.
- `custom/config/wireguard_agent/wg0.conf.j2` — the control node's own `wg0.conf` (peer: `Address = 10.105.0.2/24`, `PersistentKeepalive`). Rendered directly to `/etc/wireguard/wg0.conf` on the control node itself by `playbook/wsl/add-peer.yml` (the only playbook in this repo that touches the machine running Ansible rather than `custom/` output or a remote host — needs `become: true` for the apt install and the `/etc/wireguard/` write). Its `[Peer]` block's `Endpoint` is deliberately left commented out — the VM hasn't booted yet at build time, so its eventual DHCP IP is unknown; `add-peer.yml`'s final `debug` task tells the user to fill it in and `wg-quick up wg0` manually once the VM's IP is known, mirroring the existing manual `known_hosts` IP fill-in step.
- Inside `preseed.cfg.j2`, the `wireguard-tools` package and the `late_command` lines that copy `wg0.conf`, enable `wg-quick@wg0`, rewrite `sshd_config`'s `ListenAddress` to `10.105.0.1`, and drop a `ssh.service.d/wireguard.conf` systemd override making `ssh.service` `After=`/`Requires=` `wg-quick@wg0.service` are all plain, unconditional lines — no Jinja conditionals at all. (An earlier, opt-in version of this feature needed a Jinja-conditional version of this block and hit a real whitespace-handling bug doing it — `trim_blocks`/`lstrip_blocks` eating the newlines around `{% if %}`/`{% endif %}` and silently corrupting the `\`-continued `late_command` string — that whole problem disappeared along with the conditional when WireGuard became mandatory; it's not a concern in the current unconditional code.)
- **Safety tradeoff, explicitly accepted by the user**: making `ssh.service` depend on `wg-quick@wg0.service` means that if WireGuard fails to come up for any reason, `sshd` never starts — and since `charlie` has no password and root login is disabled, there is *no* fallback login path at all, not even via the ESXi console. The user's reasoning: this VM is already a disposable, rebuild-from-scratch-if-broken environment by design (no rescue path even without WireGuard) — this just extends that same accepted tradeoff to one more subsystem, not a new category of risk. An earlier, safer alternative (firewall rule restricting the SSH port to the `wg0` interface instead of binding `sshd` to the tunnel address, so a down WireGuard interface means "unreachable" rather than "won't start") was offered and explicitly declined in favor of the simpler literal approach.
